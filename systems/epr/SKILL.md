# EPR — Error Pattern Registry

발생한 오류를 분류·축적하고, 유사 작업 시 패턴 매칭으로 사전 경고하여 같은 실수를 반복하지 않는 시스템.

**핵심 원칙:**
1. 오류는 **학습 자산**이다 — 발생 시 반드시 기록하고, 해결책과 함께 축적한다
2. 오류 패턴은 **3계층**(사용자/프로젝트/범용)으로 분류한다
3. 기록만으로는 부족하다 — **작업 시작 전 자동 조회**하여 사전 경고한다
4. 오류 패턴은 **일반화**한다 — 특정 사례가 아닌 원리 수준으로 추상화한다

## 레지스트리 구조

### 디렉토리 레이아웃

```
{error-registry-root}/
├── user-level/
│   ├── common-mistakes.md        # 사용자 개인의 반복 실수 패턴
│   └── preferences.md            # 수정 후 사용자가 선호한 방식
├── project-level/
│   └── {project-name}/
│       ├── known-issues.md       # 이 프로젝트 특화 함정
│       └── resolved-patterns.md  # 해결된 패턴 (규칙으로 승격 가능)
└── global/
    └── anti-patterns.md          # 범용 안티패턴 (모든 프로젝트 공통)
```

### 배치 경로
- **Antigravity**: `.gemini/config/error-registry/`
- **프로젝트별**: 각 workspace의 `_workspace/.error-registry/`
- **범용**: `.gemini/config/error-registry/global/`

## 오류 패턴 기록 형식

### 단일 패턴 엔트리

```markdown
### EP-{NNNN}: {패턴 제목}
<!-- EPR: id=EP-0001, level=user|project|global, severity=critical|high|medium|low -->
<!-- EPR: created=2026-06-07, last_triggered=2026-06-07, trigger_count=3 -->

**증상**: {어떤 현상이 발생했는가}

**근본 원인**: {왜 발생했는가 — Why-First 원칙}

**잘못된 접근**: 
```
{이렇게 하면 문제가 발생한다 — 구체적 예시}
```

**올바른 접근**:
```
{이렇게 해야 한다 — 구체적 예시}
```

**탐지 조건**: {이 패턴이 재발할 수 있는 상황을 기술}
- 트리거 키워드: [{관련 키워드 목록}]
- 관련 파일/도구: [{해당되는 경우}]

**적용 범위**: {언제 이 패턴이 유효한지, 예외는 무엇인지}
```

### 기록 원칙

1. **일반화**: "Q4 매출 열을 변환하라" → "수치를 암시하는 열명은 자동 변환"
2. **증거 기반**: 실제 발생한 오류만 기록 (가설적 위험은 REE의 규칙으로)
3. **Why-First**: 증상보다 **원인**을 우선 기술 — 원인을 이해하면 변형에도 대응 가능
4. **구체적 예시**: 올바른/잘못된 접근 모두에 실행 가능한 예시 포함

## 오류 분류 기준

### 3계층 분류 매트릭스

| 기준 | User Level | Project Level | Global |
|------|-----------|--------------|--------|
| **범위** | 이 사용자에게만 해당 | 이 프로젝트에서만 해당 | 모든 작업에 공통 |
| **예시** | "사용자가 항상 한국어 보고서를 선호하는데 영어로 작성함" | "이 프로젝트의 API는 v2를 사용해야 하는데 v1을 호출" | "JSON 파싱 전 유효성 검사 없이 파싱 시도" |
| **이동** | 다른 사용자에게도 보편적이면 → Global 승격 | 다른 프로젝트에서도 동일하면 → Global 승격 | — |
| **수명** | 사용자가 습관을 바꾸면 삭제 | 프로젝트 변경 시 업데이트 | 영구 보존 |

### 심각도 분류

| 심각도 | 기준 | 사전 경고 방식 |
|-------|------|--------------|
| **Critical** | 데이터 손실, 보안 위협, 되돌릴 수 없는 변경 | ⛔ 작업 차단 + 사용자 확인 필수 |
| **High** | 산출물 품질 심각 저하, 대규모 재작업 필요 | ⚠️ 명시적 경고 + 회피법 제시 |
| **Medium** | 부분적 품질 저하, 수동 수정 필요 | 💡 권장사항으로 표시 |
| **Low** | 스타일/형식 불일치, 사소한 비효율 | 📝 참고사항으로 기록 |

## 패턴 매칭 및 사전 경고

### Pre-flight 조회 프로토콜

작업 시작 전 (REE의 Pre-flight와 연동) 다음을 수행한다:

1. **작업 키워드 추출**: 사용자 요청에서 주요 키워드/도메인/기술 추출
2. **3계층 스캔**:
   - User Level: `common-mistakes.md`의 모든 항목 스캔
   - Project Level: 현재 프로젝트의 `known-issues.md` 스캔
   - Global: `anti-patterns.md` 스캔
3. **탐지 조건 매칭**: 각 패턴의 `탐지 조건 > 트리거 키워드`와 현재 작업 키워드 대조
4. **매칭된 패턴 보고**:

```markdown
## ⚠️ EPR Pre-flight 경고

이전에 유사한 상황에서 다음 오류가 발생한 적이 있습니다:

### [EP-0003] API 버전 불일치 (심각도: High)
- 이전 발생: 2026-06-01 (2회)
- 증상: v1 API 호출 → deprecated 응답
- 권장: v2 엔드포인트 사용 (`/api/v2/...`)

### [EP-0012] 한국어 인코딩 누락 (심각도: Medium)
- 이전 발생: 2026-05-28 (1회)
- 증상: CSV 저장 시 한글 깨짐
- 권장: `encoding='utf-8-sig'` 명시
```

### 매칭 알고리즘

단순 키워드 매칭 + 컨텍스트 유사성 판단:

1. **키워드 직접 매칭**: 트리거 키워드가 작업 요청에 포함되면 매칭
2. **도구/파일 매칭**: 사용 예정인 도구/파일이 패턴의 관련 도구/파일과 일치하면 매칭
3. **도메인 유사성**: 패턴의 프로젝트/도메인과 현재 작업의 도메인이 유사하면 매칭
4. **임계치**: 2개 이상의 조건이 매칭되면 경고 출력

## 오류 발생 시 등록 워크플로우

```
오류 발생
  │
  ├─→ 1. 오류 분석: 증상, 근본 원인, 해결책 파악
  │
  ├─→ 2. 기존 패턴 조회: 이미 등록된 유사 패턴이 있는가?
  │      ├─ 있다 → trigger_count 증가 + 해결책 업데이트
  │      └─ 없다 → 신규 패턴 등록
  │
  ├─→ 3. 분류 결정: user / project / global
  │
  ├─→ 4. 일반화: 특정 사례 → 원리 수준 추상화
  │
  └─→ 5. 기록: 해당 .md 파일에 패턴 엔트리 추가
```

## REE 연동

- EPR의 `resolved-patterns.md`에서 안정적으로 검증된 패턴은 REE의 **규칙으로 승격**할 수 있다
- 승격 기준: 3회 이상 발생 + 해결책이 검증됨 + 범용적 적용 가능
- 승격 시 EPR 엔트리에 `<!-- PROMOTED: rule_id=R-XXX -->` 마커 추가

## ICIP 연동

- 서브에이전트의 게이트 평가에서 "재작업 필요" 판정 시 → EPR에 패턴 등록 검토
- 반복적인 목적 드리프트 → 패턴화하여 향후 분기 설계 시 사전 경고

## 에러 핸들링
- 레지스트리 파일이 없는 경우: 자동 생성 (빈 템플릿)
- 레지스트리가 너무 커진 경우 (100개 이상): 6개월 이상 미트리거 패턴을 archive로 이동
- 패턴 간 충돌 (A의 올바른 접근이 B의 잘못된 접근인 경우): 적용 범위를 세분화하여 분리

## Agent-First CLI Synergy: Anti-Rationalization (합리화 방지)
Justin Poehnelt의 'Agent DX 최적화' 원칙에 따라, EPR은 단순한 코드 레벨의 오류(Bug)뿐만 아니라 **에이전트의 워크플로우 회피 및 변명(Rationalization)** 패턴을 사전에 차단하는 레지스트리 역할도 수행한다.

### 합리화 방지 논리 등록
에이전트가 단계를 건너뛰기 위해 흔히 사용하는 변명(예: "이 코드는 너무 간단해서 테스트가 불필요하다", "보안 리뷰는 배포 직전에 하겠다")을 패턴화하여 등록하고, 이에 대한 **사전 반박 논리(Rebuttal)**를 함께 저장한다.
에이전트가 워크플로우를 회피하려는 징후를 보일 때, 오케스트레이터는 이 반박 논리를 즉각 주입하여 변명을 무효화하고 즉각적인 증거 제출을 강제한다.
