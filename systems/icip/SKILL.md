# ICIP — Ishikawa Context Isolation Protocol

Main 컨텍스트의 목적을 보존하면서 하위 작업을 병렬로 위임하고, 결과가 목적에 부합하는지 평가하여 통합하는 프로토콜.

**핵심 원칙:**
1. Main 컨텍스트는 **사령관**이다 — 직접 작업하지 않고, 위임하고, 평가하고, 통합한다
2. 목적 앵커는 **불변(immutable)**이다 — 생성 후 수정되지 않으며, 모든 게이트에서 참조된다
3. 서브에이전트의 중간 산출물은 Main으로 **역류하지 않는다** — 구조화된 요약만 반환된다
4. 이시카와 다이어그램처럼 **원인의 가지(branch)**를 기록하여 탐색 범위를 시각화한다

## Phase 1: 목적 앵커 설정 (Purpose Anchor)

작업 시작 시 반드시 `_workspace/00_purpose_anchor.md`를 생성한다.

### 목적 앵커 필수 항목

```markdown
# Purpose Anchor
<!-- ANCHOR: IMMUTABLE — 이 파일은 생성 후 수정하지 않는다 -->

## 핵심 목적
{사용자가 달성하려는 최종 목표를 1-2문장으로}

## 성공 기준
1. {목표 달성 여부를 판단할 구체적 기준 1}
2. {기준 2}
3. {기준 3}

## 범위 제한
- 포함: {반드시 다뤄야 할 것}
- 제외: {명시적으로 다루지 않을 것}

## 최종 산출물
- 형태: {보고서/코드/분석/계획 등}
- 대상 독자: {누가 읽는가}
```

### 앵커 작성 규칙
- 사용자의 원문 요청을 **해석하지 않고 그대로** 포함한다 (변환 시 의도 손실 위험)
- 모호한 부분은 사용자에게 확인한다 (추측 금지)
- 앵커 파일은 `_workspace/` 내에서 항상 **첫 번째로 읽히는** 파일이다

## Phase 2: 분기 설계 (Branch Design)

### 이시카와 분기 맵

병렬 작업을 설계할 때 `_workspace/01_branch_map.md`에 분기 구조를 기록한다:

```markdown
# Branch Map — 이시카와 분기 구조

## 목적: {앵커에서 복사}

## 분기 구조
```
          ┌─── [Branch A: {이름}] ── 담당: {에이전트}
          │    목표: {이 분기의 구체적 질문}
          │    기대 산출물: {파일명}
          │
[목적] ──┼─── [Branch B: {이름}] ── 담당: {에이전트}
          │    목표: {이 분기의 구체적 질문}
          │    기대 산출물: {파일명}
          │
          └─── [Branch C: {이름}] ── 담당: {에이전트}
               목표: {이 분기의 구체적 질문}
               기대 산출물: {파일명}
```

## 분기 간 관계
- {Branch A}와 {Branch B}의 교차점: {어떤 발견이 서로 영향을 줄 수 있는지}
- 의존성: {있다면 명시}
```

### 분기 설계 원칙
1. 각 분기는 **독립적으로 수행 가능**해야 한다 (의존성 최소화)
2. 각 분기에 **구체적 질문**을 부여한다 — "조사해줘"가 아닌 "X가 Y에 미치는 영향을 수치로 확인해줘"
3. 분기 수는 **3-5개**가 적정 — 7개 이상이면 2단계 계층화를 검토

## Phase 3: 서브에이전트 위임 (Delegation)

### 반환 필터 (Return Filter)

서브에이전트에게 작업을 위임할 때, 반드시 **반환 형식**을 지정한다:

```markdown
## 반환 형식 (모든 서브에이전트 공통)

작업 완료 시 다음 형식으로 결과를 `_workspace/` 파일에 저장하라:

### TL;DR (3문장 이내)
{핵심 발견 요약 — Compaction 시 이 섹션만 보존됨}

### 핵심 발견 (최대 5개)
1. {발견 + 근거}
2. ...

### 목적 기여도 자기 평가
- 목적 앵커의 성공 기준 1에 대한 기여: {상/중/하 + 이유}
- 목적 앵커의 성공 기준 2에 대한 기여: {상/중/하 + 이유}

### 예상치 못한 발견
{목적 범위 밖이지만 중요할 수 있는 발견 — Main이 판단}

### 미해결 질문
{추가 조사가 필요한 사항 — 다른 분기에서 확인 가능한지 표시}

### (필수) JSON 메타데이터 및 증거 데이터
마크다운 출력 하단에 반드시 아래 JSON 형식의 메타데이터를 포함하라. 특히 `verification_evidence`가 없거나 부실하면 산출물은 전면 기각된다.
**작업 유형에 따른 증거 유형:**
- 코드 작업: 빌드 로그, 테스트 결과, 커버리지 수치
- 리서치/분석 작업: 참조 원문 출처(URL/DOI), 인용 횟수, 데이터 원본 경로
- 계획/설계 작업: 고려한 대안 목록, 선택 근거, 제약조건 매칭 결과
```json
{
  "success": true,
  "task_type": "code | research | planning",
  "verification_evidence": "{작업 유형에 맞는 기계적 증거 원문}",
  "contribution_score": 85
}
```
```

### 위임 시 프롬프트 필수 포함 사항
1. 목적 앵커 전문 (복사해서 포함)
2. 이 분기의 구체적 질문
3. 반환 형식
4. `다른 분기에서는 {X}를 조사 중이므로, 중복하지 말 것` (교차 인식)

## Phase 4: 목적 부합성 게이트 (Purpose Alignment Gate)

### 게이트 평가 프로토콜

각 서브에이전트의 결과가 반환될 때, Main은 반드시 다음을 수행한다:

1. **목적 앵커 재로드**: `_workspace/00_purpose_anchor.md`를 다시 읽는다
2. **결과 대조**: 서브에이전트 결과의 `목적 기여도 자기 평가`와 Main의 판단을 대조한다
3. **드리프트 감지**: 결과가 목적에서 벗어났는지 평가한다

```markdown
## 게이트 평가 기록 (Main이 작성)

### Branch {X} 평가
- 서브에이전트 자기 평가: {상/중/하}
- Main 평가: {상/중/하}
- 괴리 여부: {없음 / 서브가 과대평가 / 서브가 과소평가}
- 목적 부합 판정: ✅ 통과 / ⚠️ 부분 채택 / ❌ 재작업 필요
- 조치: {통합에 포함 / 범위 축소 후 포함 / 재위임}
```

### 드리프트 대응
| 드리프트 수준 | 조치 |
|-------------|------|
| 없음 | 결과를 그대로 통합에 포함 |
| 경미 (방향은 맞으나 깊이 부족) | 보충 질문을 추가하여 같은 에이전트에 재위임 |
| 중대 (목적에서 이탈) | 결과를 `예상치 못한 발견`으로만 기록하고, 분기를 재설계 |
| 심각 (목적과 무관) | 결과를 폐기하고, 분기 설계 자체를 재검토 |

## Phase 5: 통합 (Integration)

### 통합 원칙
1. 통합은 **Main이 직접** 수행한다 (서브에이전트에게 위임하지 않음)
2. 각 분기의 `TL;DR`을 먼저 모아서 **전체 그림**을 파악한 후, 상세를 선택적으로 참조한다
3. 통합 산출물에 반드시 **출처 분기**를 표시한다 (어떤 발견이 어느 분기에서 왔는지)
4. 분기 간 **상충되는 발견**이 있으면 명시적으로 기록하고 Main이 판단을 내린다

### 통합 산출물 구조
```markdown
# [최종 산출물 제목]

## 목적 달성도 평가
- 성공 기준 1: {달성/부분달성/미달성} — 근거: {Branch X, Y에서}
- 성공 기준 2: ...

## 핵심 발견 통합
{분기별 핵심 발견을 하나의 일관된 서사로 통합}

## 분기 간 상충
{있다면 기록 + Main의 판단}

## 한계 및 후속 과제
{이번 작업에서 해결하지 못한 것}
```

## 에러 핸들링
- 서브에이전트가 반환 형식을 지키지 않을 때: Main이 강제로 구조화하여 게이트 평가 진행
- 서브에이전트가 타임아웃일 때: 완료된 부분까지만 반환받고, 미완성 표시 후 게이트 통과
- 모든 분기가 목적에서 이탈할 때: 목적 앵커 자체를 사용자에게 재확인 요청

## Agent-First CLI Synergy: JSON Payload & Defense-in-depth
Justin Poehnelt의 'Input Hardening Against Hallucinations(환각 방어)' 원칙에 따라, ICIP 게이트 통과 요건은 자연어 프롬프팅에서 **엄격한 스키마 검증(Defense-in-depth)**으로 격상된다.

### JSON 페이로드 위임
Main 오케스트레이터가 서브에이전트에게 작업을 위임할 때, 단순 줄글이 아닌 기계 판독 가능한 JSON(`--json` 형태)으로 `목표, 제약사항, 반환 스키마`를 전달하여 추론의 모호성을 제거한다.

### 산출물 강제 검증 (Validation) 및 증거 데이터(Non-Negotiable Evidence) 필수화
서브에이전트는 결과를 마크다운뿐만 아니라 구조화된 JSON 메타데이터(예: 성공 여부, 기여도 점수, 추출된 핵심 지표 등)로 함께 반환해야 한다. 
특히, Justin Poehnelt의 "에이전트는 신뢰할 수 없는 오퍼레이터다" 원칙에 따라 ICIP 게이트 통과를 위해 "verification_evidence"(증거 데이터) 페이로드가 반드시 포함되어야 한다. 이 필드에 실제 런타임 로그, 빌드 성공 메시지, 테스트 커버리지 수치 등 기계적 증거가 없으면, 내용이 훌륭해도 ICIP는 가차 없이 Reject(기각)하고 재작업을 지시한다.
